# PadDisplay 0.2.2 固定签名与权限恢复

## 已确认的原因

用户在系统设置中已开启 PadDisplay 的权限，但运行中的 0.2.1 仍显示需要授权。系统 `tccd` 日志确认：辅助功能记录保存的旧身份要求是 `cdhash 6ad22632764065bac3ba81d884baa9004778364c`，当前安装包的身份要求是 `cdhash 7abf9d76dacc7530e7e5e97892e5dbc9c3ebdaae`，匹配失败并返回 `-67050`。

旧打包脚本默认使用 ad-hoc 临时签名。这种身份要求绑定具体代码哈希，重新构建后会变化；系统设置中的旧开关开启，并不表示新二进制满足旧授权。[Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements/) 说明应用身份要求用于跨版本识别及隐私权限关联。

## 本次修改

- 打包版本更新为 0.2.2，内部版本号为 5。
- 正式应用从被 Git 忽略的 `script/signing.identity.local` 读取固定证书 SHA-1；`SIGN_IDENTITY` 可显式覆盖。当前本机已配置一张有效的 Apple Development 证书。
- 缺少配置、证书不可用或指定临时签名 `-` 时，构建会中止，不会自动选用其他证书。检查在结束项目旧进程之前执行。
- 保持 Bundle ID `local.PadDisplay`。私钥仍由系统钥匙串管理，没有导出到项目。
- UI 验证副本使用独立 Bundle ID 和临时签名，保持隔离用途。

本次没有修改显示器切换、连接识别、设备配置或界面代码。

## 验证

验证副本仅修改版本字段并使用同一证书重新签名，没有运行或发布。这个检查确认不同版本的签名数据可以变化，同时仍保持同一个应用身份；它不能代替用户重新授权后的真实连接验证。

证据位于 [`evidence/stable-signing-20261013`](../evidence/stable-signing-20261013/)。完整证书身份要求仅保留在被 Git 忽略的构建目录，公开记录不包含证书持有者邮箱或私钥。

## 安装与授权状态

构建前当前 Mac 运行的是 0.2.1，使用临时签名。iPad 虚拟屏幕由手动应用创建；输出为 2732 × 2048，逻辑桌面为 1366 × 1024。此状态不能算作自动识别已恢复。

0.2.2 已更新到 `/Applications/PadDisplay.app` 并启动，安装后的应用与验证过的打包应用逐文件一致，签名完整性检查通过。旧版本正常退出后移除了虚拟屏幕，实体显示器恢复为主显示器；两台设备的配置与自动匹配开关保持一致，UU远程的四个进程未被重启。旧应用保留为 ZIP 回滚副本，测试和备份用的重复 `.app` 已移除，系统授权列表显示正式的 PadDisplay.app。

首次证书身份授权尚待用户完成。从临时签名切换到证书签名，需要用户在系统「设备控制和数据访问／辅助功能」中移除旧 PadDisplay 项，重新添加 `/Applications/PadDisplay.app` 并开启权限。此步骤已在软件启动后交给用户；目前不能宣称自动识别已经恢复。不会改写系统权限数据库或清空其他应用的授权。

以后保持兼容的签名身份及 Bundle ID，正常升级通常可以沿用授权。证书过期、替换身份或系统 / 用户撤销权限时，仍应重新检查。当前证书适合本机开发；公开分发应使用 [Developer ID Application](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/) 和 [Apple 公证](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)。
